A. USER REGISTRATION, LOGIN, LOGOUT, AND DATA ISOLATION

Registration endpoint:
POST /api/auth/register
Request JSON:
{
  "username": "user@example.com",
  "password": "password123",
  "fullName": "John Doe",
  "phoneNumber": "+1234567890"
}
Requirements:
- `username` must be a valid email address and is the login identifier.
- `password` must meet a documented security policy and must never be stored or logged in plaintext.
- `fullName` is mandatory and non-blank.
- `phoneNumber` is mandatory and validated as a reasonable contact number, allowing international formats such as `+1234567890`.
- Enforce unique usernames/email addresses and return HTTP 409 for duplicates.
- Hash passwords using Spring Security's BCrypt password encoder or an equally suitable standard encoder.
- Return HTTP 201 and a response compatible with `{"message":"User registered successfully","userId":1}`. Never include the password/hash in any response.
- Initialise the required default categories for each new user, or otherwise provide equivalent safe, user-scoped access to immutable defaults.

Login endpoint:
POST /api/auth/login
Request JSON:
{"username":"user@example.com","password":"password123"}
Requirements:
- Authenticate with the registered username/email and password.
- Establish a real server-side HTTP session and return a session cookie for subsequent requests.
- Invalid credentials return HTTP 401 with a clear, non-sensitive error response.
- Avoid account enumeration in error messages where practical.
- Cookie settings must be appropriate for deployment: HttpOnly; Secure in HTTPS production; a suitable SameSite policy; and reasonable session expiration/timeout.

Logout endpoint:
POST /api/auth/logout
Requirements:
- Require an authenticated session unless the official test contract clearly specifies otherwise.
- Invalidate the server-side session and clear/expire the cookie.
- Return HTTP 200 with `{"message":"Logout successful"}` on success.
- Reusing a logged-out session must not grant access.

Security/data ownership:
- All API endpoints except registration and login require authentication, unless a narrowly necessary public health endpoint is documented.
- Users must be able to access only their own transactions, custom categories, and goals.
- Never trust a user ID supplied by the client to determine ownership. Derive the current user from the authenticated session.
- Ownership checks must be enforced in service/repository queries, including read, update, and delete operations. Do not leak whether another user's record exists.
- Use consistent 401/403/404 behavior. Follow the assignment/test contract where defined.
- Review CSRF handling carefully because authentication uses cookies. Prefer a secure, testable approach; inspect the official script first and document any intentional API-specific trade-off rather than accidentally breaking valid requests.

B. TRANSACTION MANAGEMENT

Create transaction:
POST /api/transactions
Example request:
{
  "amount": 50000.00,
  "date": "2024-01-15",
  "category": "Salary",
  "description": "January Salary"
}
Requirements:
- `amount` is mandatory and strictly positive.
- `date` is required, must follow `YYYY-MM-DD`, and cannot be in the future.
- `category` must reference a valid category accessible to the authenticated user. Reject missing, deleted, or otherwise inaccessible categories.
- `description` is optional, length-limited, and safely handled.
- The transaction's type (`INCOME` or `EXPENSE`) must be derived consistently from its category; do not allow contradictory client input.
- Return HTTP 201 with an appropriate representation such as `{id, amount, date, category, description, type}`.

Read/list transactions:
GET /api/transactions
Requirements:
- Return only the current user's transactions.
- Sort newest date first; apply a deterministic tie-breaker such as descending ID.
- Support filters for date range, category, and transaction type.
- Support `startDate` and `endDate` query parameters, as well as `categoryId` as shown in the specification. Also support category-name filtering if useful for compatibility, and support `type=INCOME|EXPENSE`.
- Validate ranges and parameter formats. A start date after end date should return a clear 400 response.
- Use a stable response shape compatible with `{ "transactions": [ ... ] }`.

Update transaction:
PUT /api/transactions/{id}
Example request:
{"amount":60000.00,"description":"Updated January Salary"}
Requirements:
- Only the owning user may update the transaction.
- Allow updates to the permitted fields (amount, category, description, and any other non-date field the contract allows).
- The date field is immutable after creation; reject attempts to change it, or ignore it only if required by the official test contract and document the decision. Never silently change the date.
- Revalidate amount/category and derive type from the current category.
- Return the updated transaction, normally HTTP 200.

Delete transaction:
DELETE /api/transactions/{id}
Requirements:
- Only the owning user may delete it.
- Return a clear success body such as `{"message":"Transaction deleted successfully"}`.
- Deleted transactions must no longer affect reports or savings-goal calculations.
- Return 404 for a missing/foreign record if that is the safer ownership policy and consistent with the test contract.

C. CATEGORY MANAGEMENT

Required built-in/default categories:
- INCOME: `Salary`
- EXPENSE: `Food`, `Rent`, `Transportation`, `Entertainment`, `Healthcare`, `Utilities`

Requirements:
- Default categories must always be available and must not be modified or deleted by users.
- Provide GET /api/categories. A response should be compatible with `{ "categories": [{"name":"Salary","type":"INCOME","isCustom":false}, ...] }`.
- Provide POST /api/categories with JSON such as `{"name":"SideBusinessIncome","type":"INCOME"}`.
- Custom category names must be non-blank, trimmed, length-limited, and unique per user. Handle case/whitespace consistently to prevent near-duplicate names.
- `type` must be exactly `INCOME` or `EXPENSE` (case normalisation may be applied consistently).
- Return HTTP 201 on success and HTTP 409 for duplicate names where appropriate.
- Provide DELETE /api/categories/{name}; safely support URL-encoded category names.
- A category currently used by one or more of the user's transactions cannot be deleted. Return a meaningful 409 Conflict (or the contract-compatible client error).
- Reject attempts to delete built-in categories and never allow a user to affect another user's custom category.
- Ensure transactions cannot reference nonexistent, deleted, foreign, or invalid categories.
- Seed defaults deterministically and idempotently; registration retries must not create duplicate defaults.

D. SAVINGS GOALS

Create goal:
POST /api/goals
Example request:
{
  "goalName":"Emergency Fund",
  "targetAmount":5000.00,
  "targetDate":"2099-01-01",
  "startDate":"2025-01-01"
}

Requirements:
- `goalName` is required, non-blank, and length-limited.
- `targetAmount` must be strictly positive and represented with `BigDecimal`.
- `targetDate` must be a future date relative to the actual execution date; do not copy stale sample dates that are now in the past.
- `startDate` defaults to the creation date if omitted. Validate it as appropriate and document the rule for supplied start dates.
- Create goals for the authenticated user only.
- Return HTTP 201 and a response with `id`, `goalName`, `targetAmount`, `targetDate`, `startDate`, `currentProgress`, `progressPercentage`, and `remainingAmount`.

Progress calculation:
- Each goal calculates independently from its own `startDate`.
- `currentProgress` = total income minus total expenses for the goal owner's transactions on/after the goal start date, using the agreed inclusive date rule consistently.
- `progressPercentage` is based on progress divided by target amount, expressed as a percentage. Handle negative progress, zero targets (although invalid at creation), and values above the target safely and consistently; document whether display percentage is capped at 0-100%.
- `remainingAmount` must be calculated consistently and should not misleadingly be negative; document the chosen cap behavior.
- Calculations must exclude deleted transactions and transactions belonging to other users.

Goal endpoints:
- GET /api/goals: list the authenticated user's goals, with live progress fields.
- GET /api/goals/{id}: return one owned goal and live progress fields.
- PUT /api/goals/{id}: update `targetAmount` and/or `targetDate` as permitted; validate all fields. Preserve immutable/unchangeable fields such as ownership and start date unless the assignment explicitly permits them to change.
- DELETE /api/goals/{id}: delete only the owning user's goal.
- Use suitable 200, 201, 400, 401, 403, and 404 statuses per the contract.

E. REPORTS AND ANALYTICS

Monthly endpoint:
GET /api/reports/monthly/{year}/{month}
Requirements:
- Validate year and month (month 1 through 12).
- Aggregate only the authenticated user's transactions within the selected calendar month.
- Include totals by category for income and expenses and compute `netSavings = totalIncome - totalExpenses`.
- Return a compatible shape such as:
{
  "month":1,
  "year":2024,
  "totalIncome":{"Salary":3000.00,"Freelance":500.00},
  "totalExpenses":{"Food":400.00,"Rent":1200.00,"Transportation":200.00},
  "netSavings":1700.00
}

Yearly endpoint:
GET /api/reports/yearly/{year}
Requirements:
- Validate the year.
- Aggregate the specified calendar year for the current user, grouping income and expenses by category across the year.
- Return `year`, `totalIncome`, `totalExpenses`, and `netSavings` in a compatible shape.
- Totals must be based on actual surviving transactions and exact decimal arithmetic. Empty periods must return a valid empty/zero report, not 500.
- Use deterministic category ordering where practical.

============================================================
Use the assignment's endpoints and JSON field names as the compatibility baseline. Avoid unnecessary path/field renaming.

Required API endpoints:
- POST   /api/auth/register
- POST   /api/auth/login
- POST   /api/auth/logout
- POST   /api/transactions

- PUT    /api/goals/{id}
- DELETE /api/goals/{id}
- GET    /api/reports/monthly/{year}/{month}
- GET    /api/reports/yearly/{year}

Status code expectations:
- 2xx: successful requests.
- 400 Bad Request: malformed JSON, invalid fields, invalid date/range, unsupported enum, or validation failure.
- 401 Unauthorized: unauthenticated request, invalid credentials, or expired/invalidated session.
- 403 Forbidden: authenticated request denied by policy, where revealing the resource's existence is safe and contract-compatible.
- 404 Not Found: missing resources; foreign-owned resource handling must be consistent and must not leak sensitive data.
- 409 Conflict: duplicate username/category and deletion of a category still referenced by transactions, where appropriate.
- Do not return 500 errors for known invalid inputs, missing records, duplicate values, ownership failures, or expected business-rule violations.

Implement:
- Request DTO validation using annotations plus service-level business validation.
- A central exception handler returning a consistent JSON error format with a useful message and, where helpful, field-level validation errors.
- No stack traces, SQL details, password information, or internal secrets in client responses.
- Sensible pagination may be added only if it does not break expected responses or official tests; if added, retain backward-compatible behavior.
- Consistent JSON serialization for dates and decimals.
- A health endpoint suitable for platform health checks may be provided without exposing sensitive information.
